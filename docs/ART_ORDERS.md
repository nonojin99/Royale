한 유닛씩 이 문서를 보고 생성 → 자르기 → 확인. **§1을 그대로 복사해 붙이고
§4에서 해당 유닛 줄만 바꿔 넣으면 된다.**

## 1. 생성 프롬프트 (공통 부분 — 그대로 복사)

```
2행 5열 스프라이트 시트를 만들어 줘.

[형식]
- 투명 배경 PNG. JPG 금지.
- 1행: 걷기 5프레임 (왼발 → 중간 → 오른발 → 중간 → 정지 순환)
- 2행: 공격 5프레임 (0번은 공격 전 중립 자세, 2~3번에 타격 순간)
- 두 행의 캐릭터를 **완전히 같은 크기, 같은 디자인**으로.
- 프레임 번호나 라벨 같은 글자를 이미지에 넣지 말 것.

[구도]
- 3/4 탑다운 (위에서 약 45도 내려다본 각도).
- 캐릭터는 화면 아래쪽(보는 사람 쪽)을 향해 서 있다.
- 광원은 왼쪽 위, 그림자는 오른쪽 아래.
- 각 프레임 안에서 가로 중앙, 발이 아래에서 약 12% 지점.
- 프레임끼리 겹치지 않게 좌우 여백을 넉넉히.
- **바닥 그림자를 그리지 말 것.** 게임이 발밑에 팀 색 링을 따로 그린다.

[화풍]
- 2D 픽셀아트 느낌의 게임 스프라이트. 진한 외곽선과 또렷한 명암.
- 실사풍·3D 렌더링 느낌 금지.
- 배경 요소(바닥, 그림자 원, 이펙트 잔상) 넣지 말 것. 캐릭터만.

[캐릭터]
<< §4에서 해당 유닛 줄을 여기에 붙여넣기 >>
```

### 왜 이 규격인가

| 규칙 | 어기면 |
|---|---|
| 투명 PNG | 체크무늬가 픽셀로 구워져 유닛마다 회색 사각형이 따라붙는다 |
| 한 장에 2행 | 따로 뽑으면 디자인이 어긋난다 — `gnawer`는 걷기가 거미, 공격이 전갈로 나왔다 |
| 두 행 같은 크기 | `devourer`가 공격에 들어가는 순간 크기가 튀었다 |
| 0번이 중립 자세 | 몸 크기 기준으로 쓴다. 여기에 이펙트가 있으면 몸이 작아진다 |
| 라벨 금지 | 이미지에 구워지면 잘라내야 하고, 안 자르면 유닛이 2.5배 작아진다 |
| 발이 12% 지점 | 발밑 팀 색 링과 어긋난다 |
| 바닥 그림자 금지 | 그림자만큼 발 위치가 아래로 밀리고, 팀 색 링과 겹쳐 지저분해진다 |

### 결과가 이상할 때 덧붙이는 문장

한 번에 안 나오면 프롬프트를 새로 짜지 말고 아래 문장만 골라 붙인다.

| 증상 | 덧붙일 문장 |
|---|---|
| **완전 옆모습으로 나옴** | `옆모습(프로필) 금지. 캐릭터의 얼굴과 가슴이 보는 사람을 향하고, 카메라가 그 위 45도에 있다. 등을 보이지도 말 것` |
| 몸이 통짜 덩어리로 보임 | `팔다리를 몸 바깥으로 벌려서, 검은색으로 채워도 무엇인지 알아볼 수 있는 윤곽을 만들 것` |
| 걷기 5프레임이 다 똑같음 | `프레임마다 다리 위치를 확실히 다르게. 몸통 높이도 걸음에 따라 오르내리게` |
| 걷기와 공격의 디자인이 다름 | `두 행은 완전히 같은 개체다. 색, 부속지 개수, 무늬가 하나도 달라선 안 된다` |
| 흐릿하고 물렁해 보임 | `모든 형태에 진한 어두운 외곽선. 명암은 3단계로만 딱딱 끊어서. 부드러운 그라데이션 금지` |

## 2. 진행 체크리스트

**24종 전부 새로 만든다.** 지금 게임에 들어 있는 이미지는 규격이 정립되기 전에
받은 것이라 전부 교체 대상이다. 새 파일이 같은 이름으로 들어오면 덮어쓴다.

### 먼저 한 마리로 화풍을 확정할 것

24종을 각각 다른 생성 배치로 뽑으면 **화풍이 흩어져서 화면이 조잡해진다.**
색감·외곽선 굵기·디테일 밀도가 제각각이 되기 때문이다.

1. `rifleman` 하나를 먼저 뽑는다
2. 잘라서 게임 화면에서 확인한다 (아래 §5)
3. 마음에 들면 **그 이미지를 스타일 참조로 붙여서** 나머지를 뽑는다

이 순서를 지키면 나중에 전부 다시 만드는 일이 없다.

## 2.5 기지 이미지

유닛과 달리 **단일 이미지 한 장**이다 (시트 아님). 종족별로 본진·확장 두 장.

- 원본: `art-src/<종족>_main.png` / `<종족>_expansion.png`
  (steel / swarmhive / covenant)
- 규격: 투명 배경, 3/4 탑다운, 광원 왼쪽 위. 본진이 확장보다 크고 화려하게 —
  게임에서 본진 2.4타일 vs 확장 1.8타일로 그려지므로 원본에서도 위계가 보여야 한다
- 바닥 그림자 금지 (팀 색 링을 게임이 그린다)

처리:

```bash
node tools/dealpha.mjs ../../art-src/steel_main.png          # 배경이 구워졌으면
node tools/base-art.mjs ../../art-src/clean/steel_main.png --faction steel --kind main
```

`public/art/bases/<종족>.<종류>.png` 로 저장되고, manifest의 `bases`에
`{"steel": ["main"]}` 식으로 적으면 나온다. 없는 종족·종류는 도형 폴백.

### 본진·확장이 한 장에 격자로 들어온 경우

`--grid 행x열 --pick 행,열`로 칸 하나를 골라낸다 (둘 다 1부터 센다).
2행 5열이면 1행이 본진, 2행이 확장, 열은 발광이 세지는 단계다 — **1열이 중립
상태**이므로 정지 이미지로는 1열을 쓴다.

```bash
node tools/dealpha.mjs ../../art-src/steel.png --shadow
node tools/base-art.mjs ../../art-src/clean/steel.png \
     --grid 2x5 --pick 1,1 --faction steel --kind main
node tools/base-art.mjs ../../art-src/clean/steel.png \
     --grid 2x5 --pick 2,1 --faction steel --kind expansion
```

칸은 이미지를 균등 분할해서 자른다. 마지막 열의 발사 이펙트처럼 칸 밖으로
삐져나온 그림이 있으면 옆 칸에 섞일 수 있어서, 그럴 때는 경고를 찍는다.

원본에서 확장이 본진보다 작게 그려져 있어도 상관없다 — **화면 크기는 코드가
정한다** (본진 2.4타일, 확장 1.8타일). 도구는 각 칸을 따로 256×256에 채운다.

## 2.6 일꾼과 미네랄

유닛도 기지도 아니다. **가로 한 줄 스트립** 한 장씩이고, `strip.mjs`가 만든다.

| | 파일 | 쓰는 칸 | 매니페스트 |
|---|---|---|---|
| 일꾼 | `art/worker.png` | 1행 5칸 (걷기) | `"worker": { "frames": 5, "fps": 8 }` |
| 미네랄 | `art/mineral.png` | 10칸 전부 (변형) | `"mineral": { "frames": 10, "fps": 8 }` |

미네랄은 애니메이션이 아니라 **변형 모음**이다. 기지마다 덩이 4개가 놓이는데
지점 번호와 순번으로 칸을 골라서, 기지끼리 다르게 생기되 매 프레임 같은 모양이
유지된다.

```bash
node tools/dealpha.mjs ../../art-src/worker.png --shadow
node tools/strip.mjs ../../art-src/clean/worker.png --out worker.png \
     --grid 2x5 --cell 64 --take 1,1-1,5
node tools/strip.mjs ../../art-src/clean/mineral.png --out mineral.png \
     --grid 2x5 --cell 64
```

`--take`를 빼면 격자 전체를 행 우선으로 편다. **배율은 칸마다 따로 잡지 않고
가장 큰 칸 기준 하나만 쓴다** — 원본의 크기 차이가 남아야 덩이가 자연스럽게
들쭉날쭉해진다.

화면에서는 덩이 0.85타일, 일꾼 0.7타일로 그린다. 기지 하나에 덩이 4개와
일꾼 8기가 폭 1.65타일 안에 들어가므로 유닛 규격(2타일)을 쓰면 서로 뭉개진다.

## 2.7 이펙트

4행 6열 시트 한 장을 `art-src/fx.png`로 받아 24칸 스트립으로 편다.
행 구성: **1행 투사체 · 2행 착탄 · 3행 폭발 · 4행 연기**. 칸 번호(행 우선
0~23)가 곧 의미이므로 **행과 열의 순서를 바꾸면 안 된다** — 렌더러의 FX 표
(`render.ts`의 `FX_IMPACT`/`FX_DEATH`)가 번호로 칸을 집는다.

```bash
node tools/dealpha.mjs ../../art-src/fx.png --shadow
node tools/strip.mjs ../../art-src/clean/fx.png --out fx.png --grid 4x6 --cell 64
```

매니페스트: `"fx": { "frames": 24, "fps": 8 }` (fps는 쓰이지 않는다).

지금 쓰는 칸: 착탄은 폭발 행에서 기갑단 13(주황 중), 군체 16(보라),
신념단 15(청록). 죽음 연기는 4행에서 기갑단 19(회색), 군체 22(보라),
신념단 21(청록 줄기). 시트가 없으면 종족 색 링이 도형 폴백으로 나온다.

## 2.8 지형 타일셋

바닥을 코드 페인트에서 이미지 타일로 바꾸기 위한 시트다. 유닛·기지·이펙트가
전부 픽셀아트가 된 지금, 화면에서 유일하게 "그림이 아닌 것"이 바닥이다.

**타일은 유닛과 규격이 완전히 다르다.** 캐릭터가 아니라 바닥 재질이므로:

- 각 칸을 **가장자리까지 꽉 채운 불투명 정사각형**으로. 여백·투명 금지
  (투명은 칸 사이 간격에만). 유닛처럼 가운데 떠 있으면 못 쓴다
- **직부감**(바로 위에서 수직으로 내려다봄). 유닛의 3/4 탑다운과 달리
  바닥은 기울면 이어 붙일 수 없다
- **이어 붙여도 경계가 티 나지 않게** — 칸 가장자리에 큰 돌·꽃 같은
  오브젝트를 두지 말고, 질감의 밝기를 칸마다 비슷하게 유지
- 게임 화면에서 타일 하나는 30px이다. 지금의 잔잔한 체커보드 대비가
  사라지지 않도록 **질감은 잔잔하게, 명도 차이는 작게**

### 생성 프롬프트 (그대로 복사)

```
4행 6열 지형 타일셋을 만들어 줘. 2D 픽셀아트 게임의 바닥 타일이다.

[형식]
- 각 칸은 가장자리까지 꽉 채운 불투명 정사각형 타일. 칸 안에 여백 금지.
- 칸끼리는 살짝 간격을 띄울 것.
- 바로 위에서 수직으로 내려다본 직부감. 원근·기울기 금지.
- 글자·라벨 금지.

[화풍]
- 2D 픽셀아트. 질감은 잔잔하게, 한 칸 안의 명도 차이는 작게.
- 타일을 바둑판처럼 이어 붙여도 경계가 티 나지 않아야 한다.
- 칸 가장자리에 큰 오브젝트(돌, 꽃)를 두지 말 것.

[내용]
- 1행: 짙은 초원 잔디 6변형. 기본 색 #1a6b3a 근처. ①② 민무늬(밝기만 미세하게
  다르게) ③④ 풀 얼룩 ⑤ 작은 들꽃 몇 송이 ⑥ 어두운 흙 얼룩 #145a30
- 2행: 고지대의 마르고 볕이 드는 땅 6변형. 기본 색 #7d8f4e~#8a7a4a.
  ①② 민무늬 ③④ 마른 풀 ⑤ 잔자갈 ⑥ 갈라진 흙
- 3행: 절벽 조각. 고지 타일이 저지와 만나는 가장자리에 얹는 조각이다.
  ① 아래쪽 절벽면 — 타일 아래변을 따라 어두운 바위 절벽이 드러남 (#3f3626)
  ② 위쪽 능선 — 타일 위변을 따라 밝은 모래빛 능선 (#d9cf9a)
  ③ 왼쪽 가장자리 — 왼변을 따라 밝은 바위 단면
  ④ 오른쪽 가장자리 — 오른변을 따라 어두운 바위 단면
  ⑤ 절벽면 변형(①과 같되 바위 모양이 다르게) ⑥ 능선 변형(②의 변형)
  가장자리 띠를 제외한 나머지는 2행과 같은 마른 땅으로 채울 것.
- 4행: 벽·바위 6변형. 지나갈 수 없는 회색 바위 지형. 기본 색 #3f3f46,
  밝은 면 #71717a. ①② 통짜 바위 덩어리 ③④ 갈라진 바위 ⑤ 이끼 낀 바위
  ⑥ 부서진 바위. 위에서 본 바위 윗면이 칸을 꽉 채울 것.
```

### 처리

```bash
node tools/dealpha.mjs ../../art-src/terrain.png   # PNG 변환용 — 배경이 단색이면 그대로 남는다
node tools/strip.mjs ../../art-src/clean/terrain.png --out terrain.png \
     --grid 4x6 --cell 64 --bgcolor auto --inset 0.1 --stretch
```

세 옵션이 전부 필요하다는 것을 실제로 넣어 보고 알았다:

| 옵션 | 없으면 |
|---|---|
| `--bgcolor auto` | 배경이 투명이 아니라 단색으로 구워져 오면 경계를 못 잡는다 |
| `--inset 0.1` | 생성기가 타일마다 어두운 테두리를 굽는다 — 게임에서 격자 줄눈이 된다 |
| `--stretch` | 비율 유지 배치가 남기는 한두 줄의 빈 픽셀도 줄눈이 된다. 타일은 셀을 정확히 꽉 채워야 한다 |

매니페스트: `"terrain": { "frames": 24, "fps": 8 }` (fps는 쓰이지 않는다).
칸 번호(행 우선 0~23)가 곧 의미이므로 행·열 순서를 바꾸면 안 된다.

렌더러 연결은 코드 작업이다(할 일 #3). 시트가 먼저 와도 문제없다 —
없는 동안은 지금의 페인트가 그대로 나온다.

| 종류 | 행 구성 | 비고 |
|---|---|---|
| **이동 유닛** | walk + attack | 기본 |

> **군체 유닛을 새로 설명할 때 지킬 것** — 벌레라고 다 되는 게 아니다.
> `tunneler`를 네 번 뽑고 나서 정리한 것이다.
>
> 1. **몸에 붙은 특징은 반드시 흡수된다.** 나선 무늬는 달팽이 껍데기가 됐고,
>    뿔은 얼굴에 묻혀 코가 됐다. 그 유닛을 정의하는 요소는 몸의 표면이 아니라
>    **몸에서 튀어나오거나(엄니·발톱) 몸을 뚫고 열리는 것(아가리)**이어야 한다.
> 2. **다리보다 대비가 중요하다.** 처음엔 “다리가 없으면 걷기가 안 나온다”고
>    적었지만 틀렸다 — 다리 없는 `tunneler`가 결국 제일 잘 나왔다.
>    실제로 게임 크기에서 살아남은 건 **검은 아가리 + 밝은 이빨**이라는
>    명도 대비였다. 갈색 몸에 갈색 부속지를 붙이면 다리를 여섯 개 줘도 뭉갠다.
> 3. **땅에 묻지 않는다.** 바닥을 그리지 말라는 규칙과 충돌해서 흙더미가
>    딸려 오고, 그건 배경 제거로 안 지워진다. 예외는 `burrower` 하나뿐이고
>    그게 그 유닛의 정체성이다.
> 4. **위에서 봤을 때 윤곽이 달라야 한다.** 3/4 탑다운에서는 몸통 대부분이
>    가려지고 실루엣만 남는다 — `gnawer`는 낫 앞발톱, `tunneler`는 원형 아가리,
>    `devourer`는 엄니. 서로 헷갈리면 게임 화면에서 구분이 안 된다.
>    특히 **`burrower`는 `tunneler`와 같은 등급(중형 70%)의 갈색 벌레**이므로,
>    아가리를 주지 말고 단단한 등껍질만 보이게 해서 갈라 놓아야 한다.
> 5. **실존 생물 이름을 쓴다.** 도형으로 설명하면(“원형 드릴 방패”, “쐐기 몸통”)
>    생성기가 제멋대로 해석한다 — 나선 원반은 전부 달팽이 껍데기로 나왔다.
>    “사마귀”, “쥐며느리”처럼 아는 생물을 대고 거기서 한두 군데만 바꾸는 편이
>    훨씬 잘 나온다.
> 6. **공격 행에 크게 변하는 것을 하나 준다.** 벌어지는 아가리, 뻗는 발톱,
>    부풀었다 터지는 주머니처럼 프레임마다 눈에 띄게 달라지는 요소가 없으면
>    걷기와 공격이 같은 그림으로 보인다.
>
> 그리고 **1150px 원본이 아니라 게임 크기로 판단한다.** 유닛은 화면에서
> 60px(대형 90%면 54px, 중형 70%면 42px) 높이로 그려진다. 원본에서 예뻐 보이는
> 잔디테일은 전부 사라지고, 남는 건 실루엣과 명도 대비뿐이다.

## 5. 받은 뒤 처리

```bash
cd packages/client

# 1) JPG로 왔거나 배경이 구워졌으면 (아니면 건너뜀)
#    --shadow 는 발밑에 구워진 회색 그림자까지 지운다
node tools/dealpha.mjs ../../art-src/gnawer.png --shadow

# 2) 자르기 — 먼저 --dry 로 확인
node tools/slice-sheet.mjs ../../art-src/clean/gnawer.png \
     --unit gnawer --rows walk,attack --dry

# 3) 문제 없으면 --dry 빼고 실행
node tools/slice-sheet.mjs ../../art-src/clean/gnawer.png \
     --unit gnawer --rows walk,attack
```

등급은 `tools/tiers.json`이 갖고 있으므로 `--tier`를 줄 필요가 없다.
출력된 내용을 `public/art/manifest.json`에 붙여 넣으면 끝.

```bash
# 4) 화면에서 확인 — 첫 유닛은 반드시 여기까지 하고 화풍을 확정할 것
pnpm --filter @royale/server build && node packages/server/dist/index.js &
pnpm --filter @royale/client dev
# 브라우저에서 http://localhost:5173/?solo=1&faction=steel
```

화면에서 볼 것: **덩치가 코스트에 맞게 읽히는가**, 발이 팀 색 링에 붙어 있는가,
걷다가 공격으로 넘어갈 때 크기가 튀지 않는가.

### 흔한 실패

| 증상 | 원인 | 대처 |
|---|---|---|
| `JPG다 — 알파 채널이 없다` | 확장자만 png | `dealpha.mjs` 먼저 |
| `투명한 픽셀이 거의 없다` | 배경이 구워짐 | `dealpha.mjs` 먼저 |
| 프레임이 5개가 아님 | 섬광이 프레임을 이어 붙임 | `--frames 5` 추가 |
| `얇은 띠가 있다` 경고 | 라벨이 구워짐 | `dealpha.mjs --cropbottom <알려주는 %>` |
| 행이 2개로 안 나뉨 | 행 간격이 좁음 | 자동으로 높이 2등분으로 넘어감. 결과 확인할 것 |
| 발밑에 회색 얼룩 | 바닥 그림자가 구워짐 | `dealpha.mjs --shadow` (기본 채도20/밝기120) |
| `--shadow` 가 캐릭터를 갉아먹음 | 밝고 무채색인 부위가 많음 | `--shadow 16,130` 처럼 조건을 좁힌다 |

## 6. 옛 원본 처리

`art-src/`에 규격 정립 전에 받은 파일들이 남아 있다. 전부 교체 대상이므로
**새 파일을 같은 이름으로 넣으면 자연스럽게 덮인다.** 굳이 먼저 지울 필요는
없고, 지금 게임에 들어 있는 이미지도 새것이 올 때까지 자리를 채워 준다.

깨끗한 상태로 시작하고 싶으면:

```bash
rm -f art-src/*.jpg art-src/*.png
rm -rf art-src/clean
rm -f packages/client/public/art/units/*.png
# manifest.json 의 units 를 {} 로 비운다
```

지우면 화면이 다시 도형으로 돌아간다. 게임은 정상 동작한다.

## 8. 4방향 발주 표준 — 턴어라운드 시트 한 장 (라운드 10.5 확정)

**신규 유닛의 4방향은 반드시 이 방식으로 발주한다.** 실측으로 확정된
결론이다:

- 방향을 따로 생성하면 매번 다른 캐릭터가 나온다 (실패 1)
- "4행 격자, 2행은 등"이라고 행을 설명하면 전부 정면으로 나온다 (실패 2)
- **"캐릭터 턴어라운드 시트(character turnaround sprite sheet)"라는
  형식 이름을 부르면 정면+뒷모습이 한 장에 나온다 (성공)** — 생성기가
  게임 아트 자료에서 그 형식 자체를 배웠기 때문이다. 행 설명보다
  형식명이 구도를 지배한다

### 확정 프롬프트 틀 (광전사로 검증됨)

> 픽셀아트 게임 캐릭터 **턴어라운드 스프라이트 시트 (character
> turnaround sprite sheet, front and back views)**, 4행 5열 격자,
> 투명 배경. (재생성이면: 첨부 이미지와 같은 캐릭터)
>
> 캐릭터: [§4의 해당 유닛 설명 + 종족 스타일 문장]
>
> 1행: 정면 걷기 5프레임 (front view, walking toward camera, **clear leg
> movement — contact, down, passing, up gait positions, legs visibly
> alternating each frame**)
> 2행: **같은 캐릭터가 180도 뒤돌아선 뒷모습 걷기 5프레임 (back view,
> walking away from camera, facing away, same clear leg movement)** —
> 투구 뒤통수와 등판만 보이고 눈이 보이지 않음
> 3행: 정면 공격 5프레임 — **무기가 5프레임 내내 켜져 있고** 팔 각도만
> 프레임마다 변함
> 4행: 뒷모습 공격 5프레임 (back view, attacking)
>
> 모든 칸에서 같은 캐릭터, 같은 크기, 같은 발 위치. 칸 사이 여백 균일.

**걷기 행에는 보행 단계를 반드시 명시한다** — 라운드 20에서 광전사 걷기
5프레임이 전부 정지 자세로 나와 "붕 떠서 가는" 유닛이 됐다. "walking"만
쓰면 생성기가 서 있는 그림 5장을 준다. contact/down/passing/up 네 단계와
"legs visibly alternating each frame"을 걷기 행마다 붙일 것.

### 결과물 특성 (그대로 받아들인다)

- **열 수는 5를 요청해도 6~7열로 나올 수 있다** — 싸우지 말 것.
  슬라이스에서 연속 5칸만 고르면 된다 (동작 변화가 큰 구간으로)
- **칸 사이에 검은 격자선**이 그려져 나올 수 있다 — `--inset 0.1`이
  잘라내므로 문제없다
- 등 행의 디테일이 정면보다 어설퍼도 합격 — 게임 크기 42px에서 방향은
  "눈이 보이나 안 보이나 + 등판 명암"으로 읽힌다

### 처리 — 한 장에서 스트립 4벌

**0단계 — 체커보드 전처리 (필수).** 생성기가 내보낸 PNG는 투명이 아니라
회색 체커보드가 구워진 경우가 많고, 그러면 `--bgcolor auto`가 깨진다
(실측: 확대·잘림 셀이 나온다). 먼저 전처리를 돌린다:

```
node tools/clean-turnaround.mjs ../../art-src/zealot4.png /tmp/zealot4.clean.png
```

그다음 열 수를 실제 이미지에서 세고 (`--grid 4x<열수>`), 행마다 연속
5칸을 고른다. 예: 4행 7열로 나왔고 각 행의 1~5칸을 쓸 때:

```
node tools/strip.mjs /tmp/zealot4.clean.png --out units/zealot.walk.png --grid 4x7 --take 1,1-1,5 --align center --inset 0.02
node tools/strip.mjs /tmp/zealot4.clean.png --out units/zealot.walkback.png   --grid 4x7 --take 2,1-2,5 --align center --inset 0.02
node tools/strip.mjs /tmp/zealot4.clean.png --out units/zealot.attack.png     --grid 4x7 --take 3,1-3,5 --align center --inset 0.02
node tools/strip.mjs /tmp/zealot4.clean.png --out units/zealot.attackback.png --grid 4x7 --take 4,1-4,5 --align center --inset 0.02
```

원본 파일명 규칙: **`art-src/<유닛id>4.png`** (4 = 4방향 턴어라운드 원본).
이 이름으로 올라오면 담당자가 자동으로 알아보고 처리한다.

- 기존 정면 시트(`walk`/`attack`)도 **같은 장 출신으로 교체**한다
- manifest에 `walkback`/`attackback` 추가 (frames 5, fps는 기존과 동일)
- 렌더러 배선: 이동 dy가 화면 위쪽이면 등 시트 (파일럿 라운드에서)
- 기존 21종 유닛의 교체는 서두르지 않는다 — 재생성할 일이 생길 때
  이 표준으로 한 장씩 갈아탄다

## 9. 영웅 3종 + 둥지 발주 (라운드 37~38, 침공 전용)

침공 런의 **서명**이다. 전장에 하나뿐이고 20분을 함께 가므로, 잡졸보다
한 단계 크고 화려해야 한다. 지금은 색 원 + 금빛 링으로 그려진다.

**공통 지침 (세 영웅 모두)**
- 크기 등급 **대형 90%** — 같은 종족 5코 유닛(융합체·거대포식자·공성전차)과
  비슷하거나 조금 더 큼. 화면에서 "저건 영웅이다"가 실루엣으로 읽혀야 한다
- 발밑에 **금빛 이중 링**을 게임이 그린다 → 원본에 바닥 장식·그림자 금지
- 종족 스타일 문장(§4)을 그대로 앞에 붙인다. 영웅이라고 다른 색을 쓰면
  전장에서 어느 편인지 안 읽힌다 — **같은 팔레트에 위계만 올린다**
- 발주는 §8의 **4방향 턴어라운드 시트 한 장**으로 (걷기 4단계 명시 필수)

### 9.1 영웅 캐릭터 설명 (§8 프롬프트의 [캐릭터] 자리에 붙여넣기)

| id | 이름 | 등급 | 캐릭터 설명 (붙여넣기용) |
|---|---|---|---|
| `hero_commander` | 강철 사령관 | **대형 90%** | (기갑단 스타일) 회청색 지휘 장갑복을 입은 인간 지휘관. 어깨에 각진 대형 견장, 등에 접힌 통신 안테나 두 개와 표식 깃발. 한 손에 짧은 지휘봉, 다른 손에 소총. 헬멧 바이저가 **주황색으로 밝게** 빛나고 얼굴 아래쪽이 드러남. 흉갑에 주황 계급 표식. 보병(소총병)보다 확실히 크고 어깨가 넓게 |

| `hero_prophet` | 빛의 예언자 | **대형 90%** | (신념단 스타일) 부유하는 거대 외계 사제. 술사와 같은 계보지만 두 배 크고 화려함: 다리가 없고 긴 금색 예복이 공중에 떠 있으며, 머리 뒤 금색 고리가 **셋** 겹쳐 회전. 양손을 벌려 그 사이에 커다란 청록 치유 광구. 어깨에서 떨어져 부유하는 금색 합금판 넷 |

### 9.2 능동기 프레임 지시 (3·4행 공격 행에 덧붙임)

영웅의 3·4행은 "공격"이 아니라 **능동기 시전**으로 그린다 — 게임에서
게이지가 차는 순간 이 프레임이 재생되기 때문이다:

- **강철 사령관**: 3~4행은 지휘봉을 하늘로 치켜들어 좌표를 지시하는 자세
  (궤도 포격 호출). 포탄·폭발은 그리지 말 것 — 게임이 따로 그린다
- **군체 여왕**: 3~4행은 복부를 웅크려 알을 밀어내는 자세, 마지막 프레임에
  꼬리 끝이 벌어짐 (산란). 새끼는 그리지 말 것
- **빛의 예언자**: 3~4행은 두 팔을 넓게 벌리고 광구가 커지는 자세 (치유).
  광선·파동은 그리지 말 것

### 9.3 둥지 (`nest`) — 3무대의 목표물

단일 이미지 한 장(§2.5 기지와 같은 규격, 시트 아님). 원본 이름은
`art-src/nest.png`.

> 그로테스크한 외계 군체의 거대 산란 둥지. 젖은 갈색 키틴으로 된
> 돔형 구조물, 꼭대기에 벌어진 붉은 구멍에서 보라색 점액이 흐름.
> 둘레에 뼈 가시와 힘줄 같은 뿌리가 땅으로 뻗음. 표면에 알주머니 혹이
> 여럿. 3/4 탑다운, 광원 왼쪽 위, 투명 배경, 바닥 그림자 금지.
> 본진 기지보다 **크고 육중하게** — 이것을 부수는 것이 런의 결말이다.

**둥지는 기지가 아니라 '건물 유닛'이다** — 방벽·촉수와 같은 통로로 그려진다.
그래서 `bases/`가 아니라 `units/`로 들어가고, 프레임 하나짜리 idle 클립이 된다:

```bash
node tools/dealpha.mjs ../../art-src/nest.png --shadow
node tools/strip.mjs ../../art-src/clean/nest.png --out units/nest.idle.png \
     --grid 1x1 --take 1,1-1,1 --align center --inset 0.02
```

manifest.json의 `units`에 한 줄 추가:

```json
"nest": { "idle": { "frames": 1, "fps": 1 } }
```

## 10. 6행 표준 — 측면 시트 추가 (라운드 40)

오너 판정: 4행(정면·등)만으로는 **뷰가 부족하다**. 옆으로 걸을 때 정면
그림을 거울로 뒤집어 쓰므로 유닛이 "게처럼" 옆걸음한다 — 라운드 19에서
이미 한 번 걸린 문제의 뿌리다.

**렌더러는 라운드 40에 이미 배선했다.** `…side` 클립이 있으면 가로 이동이
세로보다 우세할 때 그것을 쓰고, 없으면 조용히 등/정면으로 떨어진다 —
아트가 도착하는 순서대로 유닛이 하나씩 좋아진다. 측면은 **화면 왼쪽을
향해** 그린다(오른쪽 이동은 거울상이 공짜).

| 행 | 클립 이름 | 내용 |
|---|---|---|
| 1 | `walk` | 정면 걷기 |
| 2 | `walkback` | 뒷모습 걷기 |
| 3 | `walkside` | **측면 걷기 (화면 왼쪽 방향)** |
| 4 | `attack` | 정면 공격·시전 |
| 5 | `attackback` | 뒷모습 공격·시전 |
| 6 | `attackside` | **측면 공격·시전 (왼쪽 방향)** |

### 첫 결과물에서 배운 것 (강철 사령관 1차)

받은 시트는 형식·캐릭터·팔레트가 모두 합격이었지만 두 가지가 걸렸다:

1. **뒷모습 시전 행에서 지휘봉이 깜빡였다** — 5프레임 중 둘만 손에 들려
   있어 게임에서 켜졌다 꺼진다. §8의 "무기는 5프레임 내내 켜져 있고 팔
   각도만 변한다" 규칙을 **행마다** 반복해서 못박아야 한다
2. **걷기 다리 동작이 약했다** — 특히 뒷모습 행이 거의 같은 5장.
   라운드 20의 "붕 떠서 가는" 문제와 같은 뿌리다. 걷기 행마다
   "보폭이 눈에 보일 만큼 크게, 앞뒤 다리가 프레임마다 바뀐다"를 넣는다

### 10.1 강철 사령관 2차 — 실제 결과와 처리 (라운드 41, 등록 완료)

6행을 요청해 **5행 7열**로 왔다. 행을 세어 매핑하는 것이 정답이었다:

| 시트 행·열 | 클립 | 프레임 |
|---|---|---|
| 1행 3~7 | `walk` | 5 |
| 2행 2~6 | `walkback` | 5 |
| 3행 3~7 | `walkside` | 5 |
| **4행 1~4** | `attack` | 4 |
| **4행 5~7** | `attackback` | 3 |
| 5행 1~5 | `attackside` | 5 |

- **4행이 정면 시전 넷 + 뒷모습 시전 셋으로 쪼개져 있었다.** 행 단위로만
  자르면 정면과 등이 한 클립에 섞여 유닛이 몸을 홱 돌린다. 잘라 넣으면
  "빠졌다"고 생각한 뒷모습 시전까지 공짜로 얻는다 — **행을 믿지 말고
  프레임을 눈으로 확인할 것**
- 프레임 수는 5로 맞추지 않아도 된다(4·3도 정상). manifest의 `frames`만
  맞으면 된다
- 창(연속 5칸) 선택은 **bbox로 정규화한 인접 프레임 차이**로 골랐다.
  칸 안 위치 차이는 strip이 정렬로 없애므로, 정규화 없이 재면 "많이
  움직인 창"이 아니라 "많이 어긋난 창"을 고르게 된다

### 10.2 영웅은 코드가 덩치를 준다 (§4 원칙의 유일한 예외)

첫 등록 후 화면에서 재니 **사령관이 소총병과 같은 키**였다. 당연하다 —
렌더러가 모든 유닛을 같은 높이로 정규화하므로 원본에서 아무리 크게 그려도
소용이 없다. 전장에 하나뿐인 유닛은 실루엣만으로 구분돼야 하므로
**영웅에만 렌더 배율 1.3배**를 준다(`UnitDef.hero`). 발밑 금빛 이중 링과
합쳐 한눈에 찾힌다.

앞으로 영웅 아트는 "대형 90%"를 그림 안에서 지키되, 화면 크기는 이 배율이
책임진다.
