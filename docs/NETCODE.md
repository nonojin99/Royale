# 넷코드 설계

## 0. 이 문서의 핵심 주장

> 이 게임은 **상태를 동기화하지 않는다. 입력만 동기화한다.**

유닛 좌표·HP를 네트워크로 보내지 않는다. 양쪽 클라이언트와 서버가 **완전히 동일한 시뮬레이션**을 독립적으로 돌리고, 오직 "누가 · 몇 번째 틱에 · 무엇을(유닛/기지/테크) · 어디에 했는가"만 주고받는다.

이 방식(**Deterministic Lockstep**)의 대가는 명확하다: **시뮬레이션이 단 1비트라도 어긋나면 두 플레이어는 서로 다른 게임을 하게 된다.** 그래서 이 문서의 대부분은 "어떻게 어긋나지 않게 만드는가"에 대한 것이다.

## 1. 시간 모델

```
틱레이트            20 Hz  (50ms/tick)
경기 길이           4분 = 4800틱 (+ 연장 1200틱)
커맨드 예약 여유    2틱   (서버가 명령을 미래에 예약하는 최소 거리)
시뮬레이션 지연     6틱 = 300ms  (모두가 "서버 시계보다 300ms 과거"를 시뮬레이션)
```

### 왜 300ms 뒤처져서 시뮬레이션하는가

순수 lockstep의 고전적 문제: **틱 N을 계산하려면 틱 N의 모든 플레이어 입력이 도착해야 한다.** 그대로 구현하면 매 틱마다 상대의 패킷을 기다리게 되어, 프레임이 상대 핑에 묶인다.

해결책은 **입력 지연(input delay)** 이다. 모두가 의도적으로 과거를 시뮬레이션한다:

```
                        서버 실제 시계 T_s
                              │
   ◀──── 300ms (6틱) ────────▶│
       │                      │
  모두가 여기를 시뮬레이션    │
    T_sim = T_s − 6           │
       │                      │
       │   ← 이 구간에서 커맨드가 전파될 시간을 번다
```

플레이어가 행동하면:
1. 클라가 즉시 서버로 전송 + **로컬에 "예약됨" 프리뷰**를 그린다 (반응성 확보)
2. 서버가 받아서 `execTick = max(T_s + 2, 요청틱)` 으로 확정하고 **양쪽 모두에게** 브로드캐스트
3. 각 클라의 시뮬은 아직 `T_s − 6` 지점에 있으므로, `execTick`에 도달하기까지 **최소 400ms의 여유**가 있다
4. 그 틱에 도달하면 양쪽이 동시에, 동일하게 유닛을 스폰한다

결과적으로 **명령 후 실제로 반영되기까지 약 300ms**의 지연이 생긴다. 이건 버그가 아니라 **디자인**이다 — 유닛 소환과 기지 건설에 원래 준비 시간이 있으므로 플레이어는 이를 지연으로 인지하지 않는다. (실시간 슈터라면 절대 불가능한 트레이드오프이고, 이 장르라서 가능한 것이다.)

### 클럭 동기화

클라는 주기적으로 `ping`을 보내고 서버의 틱을 받아 `T_s`를 추정한다:

```
T_s_추정 = 서버가_알려준_틱 + (왕복시간 / 2) / 50ms
```

RTT 표본의 **중앙값**을 쓴다 (평균은 스파이크 한 번에 오염된다). 추정치가 어긋나면 시뮬 속도를 ±10%만 조절해 서서히 따라잡는다 — 순간이동시키면 화면이 튄다.

## 2. 결정론을 지키는 규칙

시뮬레이션 코드(`packages/shared/src/sim.ts`)는 아래 규칙을 **전부** 지켜야 한다. 하나라도 어기면 데스싱크가 난다.

### 규칙 1 — 부동소수점 금지

모든 상태는 **정수**다. 좌표는 "밀리타일"(1타일 = 1000) 단위 정수.

```ts
// ✗ 절대 금지
entity.x += speed * dt;

// ✓ 고정소수점
entity.x += fdiv(dx * speed, dist);   // 전부 정수 연산
```

부동소수점 자체는 IEEE-754로 정의되어 있지만, **컴파일러/JIT가 곱셈-덧셈을 융합(FMA)하거나 연산 순서를 바꾸면** 결과가 갈린다. 정수는 이런 여지가 없다.

예외: `Math.sqrt`는 IEEE-754가 **정확한 반올림을 요구**하는 몇 안 되는 함수라 결정론적이다. 그래도 안전하게 정수 보정 루프를 덧붙였다 (`isqrt`).

### 규칙 2 — `Math.random()` 금지

시드 기반 PRNG(xorshift32)만 사용한다. 시드는 서버가 매치 시작 시 양쪽에 동일하게 배포한다. PRNG 상태 자체가 게임 상태의 일부이므로 스냅샷·해시에 포함된다.

### 규칙 3 — 순회 순서 고정

```ts
// ✗ 위험 — Map/Set/객체 키 순서에 의존
for (const e of entityMap.values()) { ... }

// ✓ ID 오름차순 배열
for (const e of state.entities) { ... }   // 항상 id 순 정렬 유지
```

동률 상황(같은 거리의 적 두 명)에서 **어느 쪽을 고르는지가 양쪽에서 같아야** 한다. 그래서 모든 타겟 선정의 최종 tie-break는 **엔티티 ID 오름차순**이다.

### 규칙 4 — 읽기/쓰기 단계 분리

유닛끼리 밀어내는 분리력처럼 서로를 참조하는 계산은, **먼저 전부 계산해서 배열에 담고 → 그 다음 한꺼번에 적용**한다. 순차 적용하면 앞 유닛의 이동이 뒤 유닛의 계산에 영향을 줘서 순회 순서 의존성이 생긴다.

### 규칙 5 — 시뮬레이션은 렌더링을 모른다

`packages/shared`는 DOM, `performance.now()`, 타이머를 일절 참조하지 않는다. 순수 함수 `step(state) → state`. 그래서 서버(Node)와 클라(브라우저)에서 **같은 파일**이 돈다. 이게 결정론의 근본 보장이다.

## 3. 데스싱크 감지 및 복구

규칙을 다 지켜도 버그는 난다. 그래서 감지 장치를 넣는다.

```
매 20틱(1초)마다:
  클라 → 서버 :  { t:'hash', tick: N, hash: FNV-1a(상태) }
  
  서버: 자신의 틱 N 해시와 비교
        불일치 → { t:'resync', tick: M, snapshot: 전체상태 } 전송
        클라는 스냅샷으로 상태를 덮어쓰고 그 시점부터 재개
```

**해시는 개발 중에는 소리를 지르게 만든다.** 콘솔에 데스싱크가 뜨면 그건 시뮬 코드 어딘가에 규칙 위반이 있다는 뜻이고, 조용히 리싱크로 덮으면 안 된다. 그래서 클라에 데스싱크 카운터를 UI로 노출한다.

리싱크는 **최후의 안전망**이지 정상 동작이 아니다. 정상적인 경기에서 리싱크 횟수는 **0이어야 한다.**

## 4. 서버의 역할

서버는 메시지를 중계만 하는 게 아니라 **동일한 시뮬레이션을 직접 돌린다.** 이유:

| 역할 | 설명 |
|------|------|
| **권위** | 클라가 보낸 요청을 시뮬 상태로 검증. 미네랄이 모자라면 그 커맨드는 무시된다 — 양쪽 시뮬 모두에서 동일하게. |
| **치팅 방지** | 배치 구역 위반, 해금되지 않은 유닛, 이미 점유된 기지 지점을 전부 서버 상태 기준으로 거부 |
| **데스싱크 판정** | 서버 해시가 정답 |
| **재접속** | 스냅샷을 언제든 만들어 줄 수 있음 |
| **리플레이** | `(시드 + 커맨드 목록)` 만 저장하면 경기 전체가 재현된다. **경기 하나가 수 KB.** |

마지막 항목이 이 아키텍처의 숨은 보상이다. 리플레이·관전·밸런스 분석이 거의 공짜로 따라온다.

## 5. 프로토콜

모든 메시지는 JSON (v1). 대역폭이 문제되지 않는 장르라 조기 최적화하지 않는다.
바이너리 인코딩이 필요해지는 시점은 관전자 수백 명을 붙일 때다.

### 클라이언트 → 서버

```ts
{ t:'hello', name: string, factionId?: string }
{ t:'act',   reqTick: number,
             kind: 'unit'|'base'|'tech',   // 유닛 생산 / 기지 건설 / 테크 해금
             id: string, x: number, y: number }   // x,y는 밀리타일
{ t:'hash',  tick: number, hash: number }
{ t:'ping',  ts: number }
```

### 서버 → 클라이언트

```ts
{ t:'queued' }
{ t:'match', matchId, seed, team: 0|1,
  factions: [string, string],      // 양 팀 종족 id — 시뮬은 이걸로 초기화된다
  opponent, startWallMs }
{ t:'cmd',   execTick, team, kind, id, x, y } // 확정된 커맨드 (양쪽에 동일 브로드캐스트)
{ t:'reject', reqTick, reason }               // 본인에게만
{ t:'pong',  ts, serverTick }
{ t:'resync', tick, snapshot }
{ t:'over',  winner: 0|1|-1, bases: [number, number], mined: [number, number] }
```

## 7. 리플레이

이 아키텍처의 배당금이다. 저장하는 것은 **시드와 커맨드 목록뿐**이고, 경기
하나가 수 KB다. 유닛 좌표도 HP도 저장하지 않는다 — 시뮬이 결정론적이라
같은 입력을 다시 넣으면 같은 경기가 그대로 나온다.

```ts
interface Replay {
  v, matchId, seed
  factions: [string, string]       // 재현에 필요한 유일한 상태
  players, createdAt               // 표시용 메타데이터
  commands: Command[]              // execTick 오름차순 정규화
  result: { winner, bases, mined, ticks }
  checkpoints: { tick, hash }[]    // 30초 간격
  finalHash: number
}
```

### 저장 시점에 재현성을 확인한다

`buildReplay`는 서버가 들고 있던 최종 상태를 그대로 베끼지 않는다. **기록된
커맨드만으로 시뮬을 처음부터 다시 돌려서** 결과·해시·체크포인트를 채운다.
여기서 서버 상태와 어긋나면 그 자리에서 에러 로그를 남긴다 — 재현되지 않는
리플레이를 조용히 저장하면 나중에 원인을 찾을 방법이 없다.

### 체크포인트가 하는 일

`verifyReplay`는 최종 해시만 보지 않고 30초 간격 체크포인트를 함께 대조해
**몇 번째 틱부터 갈라졌는지**를 돌려준다. 시뮬 로직을 고친 뒤 과거 리플레이가
깨졌을 때, "어디를 건드려서 깨졌는가"를 좁히는 데 이게 결정적이다.

### HTTP

```
GET /replays?limit=30    → 최근 목록 (id, 종족, 승자, 크기)
GET /replay/<matchId>    → 리플레이 JSON
```

클라이언트(GitHub Pages)와 서버(Fly.io)의 출처가 다르므로 두 엔드포인트는
`Access-Control-Allow-Origin: *`를 붙인다. 읽기 전용 공개 데이터라 문제없다.

### 뷰어의 탐색

스크럽바를 끌 때마다 0틱부터 다시 돌리면 감당이 안 되므로, `ReplayPlayer`는
최초 1회 전체 재생 중에 10초(200틱)마다 상태 스냅샷을 남긴다. 이후 임의 틱
탐색은 "가장 가까운 이전 키프레임에서 복원 → 최대 200틱 전진"으로 끝난다.
