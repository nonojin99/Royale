# 아트 파이프라인 — 캐릭터 이미지와 애니메이션 도입

이 문서는 **별도 툴로 생성한 캐릭터 이미지를 게임에 넣는 방법**과, 스타크래프트 같은 **속도감·타격감**을 만드는 방법을 정한다.

---

## 0. 가장 중요한 결론 먼저

> **타격감은 스프라이트 프레임에서 나오지 않는다. 상태 전이에 붙는 반응에서 나온다.**

스타크래프트에서 마린이 쏠 때 "맞는 느낌"을 만드는 것은 걷기 프레임이 아니라:

| 요소 | 지속 | 효과 |
|---|---|---|
| 피격 플래시 | 80ms | 맞은 쪽이 흰색으로 번쩍 |
| 총구 섬광 | 60ms | 쏜 쪽 앞에 짧은 빛 |
| 반동 | 120ms | 쏜 쪽이 뒤로 살짝 밀렸다 복귀 |
| 넉백 | 150ms | 맞은 쪽이 살짝 밀림 |
| 파편 | 300ms | 착탄점에서 작은 입자 |
| 화면 흔들림 | 100ms | 큰 타격에만 |
| 사망 | 400ms | 사라지지 않고 무너짐 |

이것들은 **전부 이미지 없이 코드로 만들 수 있고, 전부 렌더 전용**이다. 반대로 프레임 애니메이션만 있고 이게 없으면 아무리 잘 그린 그림도 밋밋하다.

그래서 도입 순서를 이렇게 잡는다:

```
1단계  유닛당 정지 이미지 1장  +  절차적 모션 + 타격 반응   ← 여기서 대부분의 체감이 나온다
2단계  걷기/공격 프레임 추가 (필요한 유닛부터)
3단계  방향별 스프라이트 (정말 필요하면)
```

**1단계만으로도 지금 원 그림보다 압도적으로 나아진다.** 그리고 생성해야 할 이미지가 유닛당 1장이라, 툴로 만드는 그림의 **일관성 문제도 최소화**된다.

---

## 1. 절대 어기면 안 되는 규칙

> **애니메이션은 시뮬레이션 상태에 절대 들어가지 않는다.**

이 프로젝트는 결정론적 lockstep이다. 시뮬 상태에 1비트라도 렌더 요소가 섞이면 두 플레이어가 서로 다른 게임을 하게 된다.

```
✗ entity.animFrame = 3          시뮬 상태 오염 → 데스싱크
✗ entity.flashUntil = Date.now()  시계 참조 → 데스싱크
✓ 렌더러가 시뮬 상태를 관찰해서 자기 쪽 타이머를 돌린다
```

애니메이션에 필요한 정보는 **이미 시뮬 상태에 다 있다.** 렌더러는 그것을 읽어서 파생시킨다:

| 필요한 것 | 시뮬에서 읽는 법 |
|---|---|
| 이동 중인가 | 직전 틱 좌표와 비교 (이미 보간용으로 저장 중) |
| 공격했는가 | `cd`가 0에서 큰 값으로 튀었는가 |
| 맞았는가 | `hp`가 줄었는가 |
| 죽었는가 | 엔티티 배열에서 사라졌는가 |
| 방향 | 좌표 변화량 또는 타겟 방향 |
| 배치 중인가 | `deploy > 0` |

## 2. 구조 — 시뮬 상태를 "시각 이벤트"로 번역한다

```
                 ┌──────────────────────────────┐
   시뮬 상태 ──▶ │  StateDiffer                 │ ──▶ 시각 이벤트
   (읽기만)      │  직전 틱 스냅샷과 비교        │     damaged / fired
                 └──────────────────────────────┘     died / spawned
                                                            │
                            ┌───────────────────────────────┤
                            ▼                               ▼
                 ┌────────────────────┐          ┌────────────────────┐
                 │ SpriteLayer        │          │ EffectLayer        │
                 │ 엔티티당 Sprite 풀  │          │ 수명 있는 임시 객체 │
                 │ 위치·틴트·플래시    │          │ 파편·섬광·잔해      │
                 └────────────────────┘          └────────────────────┘
```

핵심은 **StateDiffer**다. 매 틱 시뮬 상태를 직전 틱과 비교해 이벤트를 뽑아낸다. 이벤트는 벽시계 기반 수명을 갖는 이펙트를 낳고, 그 이펙트는 시뮬과 무관하게 자기 속도로 재생된다.

리플레이에서도 그대로 동작한다 — 리플레이 뷰어도 같은 시뮬 상태를 먹으므로 이펙트가 똑같이 나온다.

## 3. 에셋 스펙 (이미지 생성 시 지켜야 할 것)

### 3.1 파일 배치와 이름

```
packages/client/public/art/
  units/
    rifleman.png          ← 파일명 = UnitDef.id 와 정확히 일치
    flamer.png
    scoutcar.png
    ...
  bases/
    main.png
    expansion.png
  worker.png
  manifest.json           ← 어떤 유닛이 어떤 애니메이션을 갖는지
```

**파일명은 `packages/shared/src/units.ts`의 `id`와 글자 하나까지 같아야 한다.** 그래야 로더가 단순해지고, 없는 파일은 즉시 눈에 띄는 에러가 된다.

현재 유닛 id 24개:

```
기갑단   rifleman  flamer  scoutcar  bulwark  ironwalker  siegetank  gunship  carpetbomb
군체     gnawer  spitter  tunneler  spinetentacle  burrower  sporetentacle  wingswarm  devourer
신념단   zealot  strider  mystic  fusionite  lightpylon  shade  skiff  mindbreak
```

### 3.2 크기

화면에서 유닛은 **지름 약 25px**(1타일 = 30px, 유닛 반경 0.42타일)로 그려진다. 레티나·확대 여유를 두려면 원본은 그보다 크게:

| 대상 | 원본 크기 | 화면 크기 |
|---|---|---|
| 유닛 | **128 × 128** | ~25px |
| 건물 (방벽·촉수·빛기둥) | **192 × 192** | ~45px |
| 기지 | **256 × 256** | ~55~72px |

정사각형 캔버스, **투명 배경 PNG**.

JPG는 알파 채널이 없어 쓸 수 없다. JPG를 PNG로 변환하는 것도 해결책이 아니다 —
변환은 알파 채널을 만들 뿐 배경을 지우지 않으므로, 미리보기에서 투명해 보이던
체크무늬가 실제 픽셀로 구워진 채 남는다. 유닛마다 회색 사각형이 따라붙게 된다.
생성 단계에서 투명 배경으로 내보내야 하고, 슬라이서가 두 경우 모두 거부한다.

### 3.3 구도 — 이게 가장 중요하다

24장이 **같은 카메라에서 찍힌 것처럼** 보여야 한다. 흩어지면 그림 하나하나가 아무리 좋아도 게임 화면은 조잡해진다.

| 항목 | 규격 |
|---|---|
| 시점 | **3/4 탑다운** (위에서 약 45° 내려다봄). 완전 정면도, 완전 수직도 아님 |
| 방향 | **화면 아래쪽을 향해** 서 있는 자세 하나로 통일 |
| 광원 | **왼쪽 위**에서 들어옴. 그림자는 오른쪽 아래 |
| 배치 | 캔버스의 **가로 중앙**, 발/바닥이 **아래에서 약 12% 지점**에 오도록 |
| 여백 | 상하좌우 최소 8% 여백 (외곽선·글로우가 잘리지 않게) |
| 크기 기준 | 캔버스 높이 대비 — 소형 55%, 중형 70%, 대형 90% |

**크기 기준을 지키는 것이 특히 중요하다.** 물어뜯는것(2코스트)과 거대포식자(5코스트)가 같은 크기로 나오면 코스트가 시각적으로 전달되지 않는다.

크기 등급:

```
소형(55%)  물어뜯는것 · 소총병 · 활잡이류 · 일꾼
중형(70%)  화염병 · 가시뱉는것 · 광전사 · 정찰차 · 굴착충 · 밍뚜류 · 술사 · 그림자
대형(90%)  공성전차 · 거대포식자 · 융합체 · 강철거인 · 전투비행선 · 날개무리 · 부유선
```

### 3.4 팀 색 처리 — 여기서 실수하면 2배로 그려야 한다

같은 유닛이 **내 편일 때와 적일 때** 구분되어야 한다. 방법은 둘:

**(A) 틴트 마스크 — 권장**
그림에 **회색조(무채색) 영역을 의도적으로 남긴다.** 어깨 견장, 깃발, 코어, 눈 같은 부분. 렌더러가 런타임에 그 부분만 팀 색으로 물들인다.

- 장점: 유닛당 이미지 1장이면 끝
- 요구: 팀 색이 들어갈 자리를 **순수 회색(#808080 근처)** 으로 칠하고, 나머지는 채도 있는 색으로

이걸 하려면 마스크 이미지가 하나 더 필요하다: `units/rifleman_mask.png` — 팀 색이 들어갈 곳만 흰색, 나머지는 검정인 흑백 이미지.

**(B) 외곽 링 — 현재 방식, 폴백**
그림은 그대로 두고 렌더러가 팀 색 테두리를 두른다. 마스크 없이 즉시 동작하지만 구분이 덜 선명하다.

> **1단계에서는 (B)로 시작하고, 마스크가 준비되는 유닛부터 (A)로 넘어가면 된다.** 로더가 마스크 유무를 보고 자동으로 고르게 만든다.

### 3.5 프레임 애니메이션 — 시트로 받아서 자른다

**프레임은 한 장에 나란히 뽑는 것이 맞다.** 따로 뽑으면 프레임마다 색·비율·디테일이
흔들려서 이어 붙였을 때 떨린다. 생성 도구에 5프레임을 한 컷으로 요청하고, 그 시트를
`tools/slice-sheet.mjs`로 자른다.

```bash
node tools/slice-sheet.mjs 시트.png --unit rifleman --anim walk --tier small
# → public/art/units/rifleman.walk.png (128px 셀 5칸짜리 스트립)
```

`manifest.json`이 어떤 유닛이 어떤 애니메이션을 갖는지 선언한다:

```json
{
  "units": {
    "rifleman": { "walk": { "frames": 5, "fps": 10 },
                  "attack": { "frames": 5, "fps": 14 } },
    "flamer":   { "walk": { "frames": 5, "fps": 10 } }
  }
}
```

선언되지 않은 애니메이션은 있는 것으로 폴백한다(`attack`이 없으면 걷기를 계속 재생).
그래서 유닛 24개를 한꺼번에 갖출 필요 없이 **한 마리씩 점진적으로** 올릴 수 있다.

#### 프레임별로 잘라내면 안 되는 이유

프레임마다 알파 경계를 재서 각각 꽉 채워 자르면 **유닛이 떨린다.** 공격 프레임에는
섬광이 몸 밖으로 삐져나오고 걷기 프레임은 다리를 벌리므로, 프레임마다 경계 크기가
다르다. 그 상태로 같은 셀에 맞추면 프레임마다 몸통 배율이 달라진다.

그래서 슬라이서는 **모든 프레임의 합집합 경계**를 기준으로 한 번만 축소한다.
상하 바운스와 다리 벌림 같은 프레임 간 상대 움직임이 그대로 남는다 — 그 움직임이
애니메이션의 실체이므로 지워서는 안 된다.

#### 자동 검출이 실패하는 경우

섬광이 커서 프레임끼리 알파가 이어지면 구간이 뭉쳐 개수를 잘못 센다. `--frames 5`를
주면 전체 폭을 균등 분할하는 방식으로 바뀐다. 생성 도구는 프레임을 균일 격자에
올려 주므로 이쪽이 뭉친 구간을 쪼개려 애쓰는 것보다 정확하다.

#### 어떤 동작이 언제 재생되는가

| 동작 | 조건 |
|---|---|
| `attack` | 공격 쿨다운(`Entity.cd`)이 올라간 순간 = 방금 쏨. 한 바퀴만 |
| `walk` | 직전 틱 대비 좌표가 변함 |
| `idle` | 그 외. `idle`이 없으면 `walk` 첫 프레임에서 정지 |

전부 시뮬 상태에서 파생한다. §1의 규칙대로 애니메이션 상태는 시뮬에 들어가지
않는다 — 한쪽 클라이언트에만 이미지가 있어도 결정론은 유지되어야 한다.

## 4. 절차적 모션 — 이미지 없이 만드는 움직임

정지 이미지 1장만으로도 아래를 코드로 붙인다. 전부 렌더 전용이고 시뮬을 건드리지 않는다.

| 효과 | 구현 | 목적 |
|---|---|---|
| **보행 흔들림** | 이동 중일 때 `sin(t)` 로 ±3° 기울임 + 1px 상하 바운스 | 걷는 느낌 |
| **방향 반전** | 이동 x성분이 음수면 `scale.x = -1` | 좌우 구분 |
| **가속 기울임** | 이동 방향으로 5° 눕힘 | 속도감 |
| **정지 호흡** | 대기 중 1.02배 느린 스케일 펄스 | 살아있는 느낌 |
| **공격 반동** | 발사 시 타겟 반대로 4px 밀렸다 120ms에 복귀 | 타격감 |
| **피격 플래시** | 흰색 오버레이 80ms | 맞았음을 즉시 인지 |
| **피격 넉백** | 맞은 방향으로 3px 밀렸다 복귀 | 충격 전달 |
| **소환 등장** | 배치 시 0.6→1.0 스케일 + 알파 페이드 (deploy 구간) | 등장감 |
| **사망 붕괴** | 스케일 1.0→0.7, 알파 1→0, 회전 15°, 400ms | 사라지지 않고 무너짐 |

**속도감**을 만드는 핵심은 가속 기울임 + 보행 흔들림이고, **타격감**의 핵심은 피격 플래시 + 반동 + 파편이다. 이 다섯 개만 넣어도 체감이 확 바뀐다.

## 5. 이펙트 레이어

시뮬과 무관한 수명을 갖는 임시 객체들. 오브젝트 풀로 재사용한다.

| 이펙트 | 트리거 | 모양 |
|---|---|---|
| 총구 섬광 | 원거리 유닛 발사 | 짧은 삼각 빛, 60ms |
| 투사체 | 원거리 발사 → 착탄 | 작은 점이 날아감. **시각 전용** (판정은 시뮬이 이미 끝냄) |
| 착탄 파편 | 피해 발생 | 4~6개 입자 방사, 300ms |
| 광역 폭발 | splash 유닛 발사 | 확장하는 원 + 파편, 400ms |
| 잔해 | 유닛 사망 | 바닥에 남는 어두운 얼룩, 3초 페이드 |
| 기지 폭발 | 기지 파괴 | 큰 폭발 + 화면 흔들림 600ms |
| 데미지 숫자 | 피해 발생 | 위로 떠오르며 페이드 (옵션) |

> **투사체는 시각 전용이라는 점이 중요하다.** 시뮬에서 사격은 즉시 판정이 끝난다. 투사체를 시뮬 엔티티로 만들면 결정론 검증 대상이 늘고 O(n²) 부담도 커진다. 눈에는 날아가는 것처럼 보이되, 결과는 이미 정해져 있다.

## 6. 성능

| 항목 | 지침 |
|---|---|
| 스프라이트 | 엔티티당 `Sprite` 하나를 **풀에서 재사용**. 매 프레임 생성 금지 |
| 텍스처 | 로딩 시 **아틀라스로 묶기** (Pixi `Assets.load` + spritesheet). 드로우콜 급감 |
| 이펙트 | 풀 재사용, 동시 상한 (예: 파편 200개) |
| 정렬 | y좌표 기준 depth sort — 아래 유닛이 위에 그려져야 자연스럽다 |
| 화면 밖 | 아레나가 화면에 다 들어오므로 컬링 불필요 |

## 7. 남은 결정 사항

- [ ] 팀 색을 틴트 마스크(A)로 갈 것인가, 외곽 링(B)으로 유지할 것인가 → **B로 시작, 마스크 준비되면 A**
- [ ] 뒷모습(위 방향) 스프라이트를 만들 것인가 → 1단계에서는 만들지 않음. 절차적 반전으로 충분한지 실물로 확인 후 결정
- [ ] 데미지 숫자 표시 여부 → 정보량이 늘지만 화면이 지저분해질 수 있음. 옵션으로
- [ ] 유닛 상한 — 현재 없음. 매크로 게임이라 후반에 엔티티가 쌓이는데 시뮬이 O(n²)다. 스프라이트가 붙으면 렌더 부담도 는다
