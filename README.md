# 로얄 (Royale)

**1v1 실시간 매크로 전략 게임.** 일꾼이 미네랄을 캐고, 그 미네랄로 **일꾼 · 병력 · 확장 · 테크** 중 무엇에 쓸지 매 순간 고른다. 상대 본진을 부수면 승리.

**3종족 · 24유닛** — 방어형(기갑단) / 물량형(군체) / 고효율형(신념단).
유닛은 처음엔 잠겨 있고 테크트리로 해금하며, **유닛은 자기 기지 반경 안에만 배치할 수 있다** — 그래서 확장은 수입이자 전선이다.

---

## 이 프로젝트의 기술적 핵심

> **상태를 동기화하지 않는다. 입력만 동기화한다.**

유닛 좌표나 HP는 네트워크로 보내지 않는다. 두 클라이언트와 서버가 **완전히 동일한 시뮬레이션**을 각자 독립적으로 돌리고, 오직 `누가 · 몇 번째 틱에 · 무엇을(유닛/기지/테크) · 어디에 했는가`만 주고받는다 (**Deterministic Lockstep**).

경기 하나의 전체 네트워크 트래픽이 **수 KB**다. 대신 대가가 있다 — 시뮬레이션이 1비트라도 어긋나면 두 플레이어는 서로 다른 게임을 하게 된다. 그래서 시뮬레이션 코드는 **부동소수점을 일절 쓰지 않는다.** 모든 좌표·거리·속도가 "밀리타일" 단위 정수다.

```
클라 A ──┐                      ┌── 커맨드 브로드캐스트 ──▶ 클라 A (시뮬 실행)
         ├──▶ 서버 (권위 시뮬) ──┤
클라 B ──┘                      └── 커맨드 브로드캐스트 ──▶ 클라 B (시뮬 실행)
                  ▲
                  └── 매초 상태 해시 대조 → 어긋나면 스냅샷으로 리싱크
```

- **[게임 기획서](docs/GAME_DESIGN.md)** — 경제, 확장, 테크트리, 배치 구역, 유닛 AI, 밸런스 설계 의도
- **[넷코드 설계](docs/NETCODE.md)** — 시간 모델, 결정론 규칙 5개, 데스싱크 감지, 프로토콜
- **[아트 파이프라인](docs/ART_PIPELINE.md)** — 이미지 규격, 스프라이트 도입 방식, 속도감·타격감을 만드는 법
- **[완성까지 계획서](docs/PLAN.md)** — 남은 일 체크리스트와 우선순위

## 구조

```
packages/
  shared/   결정론 시뮬레이션 — 서버와 클라이언트가 이 코드를 그대로 공유한다
            fixed.ts  고정소수점 정수 수학 (부동소수점 금지)
            rng.ts    시드 PRNG (Math.random 금지)
            arena.ts  지형 / 다리 / 배치 구역
            units.ts  유닛 데이터 테이블 (밸런싱은 전부 여기서)
            factions.ts 종족·테크트리 3종 (모듈 로드 시점에 정합성 검증)
            sim.ts    ★ 틱 진행: 타겟팅 · 이동 · 전투 · 승패
            replay.ts 리플레이 포맷 · 재현 검증 · 키프레임 탐색
  server/   WS 서버 + 룸/매치메이킹 + 권위 시뮬 + 데스싱크 판정 + 연습용 봇
  client/   PixiJS 렌더러 + 클럭 동기화 + 조작 UI + 넷 계기판
```

`shared`는 DOM도 타이머도 참조하지 않는 순수 함수 덩어리다. 그래서 Node와 브라우저에서 **같은 파일**이 돌고, 그게 결정론의 근본 보장이다.

## 실행

```bash
pnpm install
pnpm --filter @royale/shared build   # 클라/서버가 shared의 빌드 결과를 참조한다

# 터미널 2개
pnpm dev:server     # ws://localhost:8787
pnpm dev:client     # http://localhost:5173
```

- 브라우저 2개(또는 시크릿 창)로 열면 서로 매칭된다.
- 혼자 테스트하려면 **`http://localhost:5173/?solo=1`** — 서버가 봇과 즉시 매칭해준다.
- 다른 서버를 가리키려면 `?server=ws://호스트:포트`, 종족을 미리 고르려면 `?faction=steel`

### 조작

- 시작 화면에서 **종족을 고른다** (기갑단 / 군체 / 신념단)
- 하단 팔레트에서 유닛을 고르고(숫자키 `1`~`8`), **내 기지 반경 안**을 클릭하면 생산된다
- **일꾼** 버튼 → 일꾼을 1기 늘린다. 수입은 기지 수가 아니라 **일꾼 수**에서 나온다. 기지 하나가 받는 일꾼은 미네랄 4덩이 × 2기 = 8기까지고, 정원이 차면 버튼이 잠긴다
- **기지 건설** 버튼(또는 `B`) → 빈 지점 근처를 클릭하면 확장한다. 일꾼 정원이 늘고 배치 구역이 앞으로 나온다
- **테크트리** 버튼 → 미네랄을 들여 유닛을 해금한다. 연구는 한 번에 하나만, 그동안은 병력을 못 뽑는다
- `Esc` 로 선택 해제

### 공중 유닛

`✈` 표시가 붙은 유닛은 **강과 다리를 무시하고 직선으로 난다.** 화면에서는 지면에 그림자를 남기고 본체가 떠 있는 것으로 구분된다.

지상 전용 공격(`화염병`, `공성전차`, `술사` 등)은 공중을 때리지 못한다. **초반에 대공 수단이 없으면 상대 공중에 아무것도 못 하고 진다** — 그래서 모든 종족이 시작 해금만으로 공중을 때릴 수 있도록 테스트로 고정해두었다.

화면 우하단의 `42ms · tick 291/297 · desync 0` 이 넷 계기판이다.
**`desync`가 0이 아니면 시뮬레이션 코드에 버그가 있다는 뜻이다** — 조용히 넘어가면 안 된다.

## 리플레이

경기가 정상 종료되면 서버가 리플레이를 저장한다. 저장하는 것은 **시드와 커맨드 목록뿐**이다 — 유닛 좌표도 HP도 남기지 않는다. 경기 하나가 **수 KB**다.

```bash
curl localhost:8787/replays              # 최근 목록
curl localhost:8787/replay/<matchId>     # 리플레이 하나 (이 JSON이 경기 전체다)
```

브라우저에서 재생:

```
http://localhost:5173/?replay=<matchId>
```

서버 연결 없이 돌아간다. 재생/일시정지(스페이스바), 0.5×~4× 배속, 스크럽바를 지원한다. 임의 지점으로 점프해도 매번 처음부터 다시 돌리지 않도록 10초마다 키프레임을 잡아둔다.

### 검증 도구

```bash
pnpm --filter @royale/server replay <파일|URL>
pnpm --filter @royale/server replay --from http://localhost:8787   # 서버의 전부
```

```
── m1-msnxvaku ──────────────────────────────────
  A (steel)  vs  B (covenant)
  승자: A (steel)   기지 1:0   채굴 21:10   길이 0:27
  커맨드 15개 · 1.3KB · 체크포인트 0개
  확장 0:0   테크 0:0
    team0 유닛 (15행동): 소총병×9, 정찰차×6
    team1 유닛 (0행동): (없음)
  ✅ 재현 검증 통과 (해시 4134867543)
```

**이 도구의 진짜 용도는 결정론 회귀 감지다.** 시뮬레이션 로직을 건드린 뒤 과거 리플레이를 돌려보면, 바뀐 것이 의도한 밸런스인지 아니면 결정론이 깨진 것인지 즉시 드러난다. 리플레이에는 30초 간격 체크포인트가 들어 있어 **어느 틱부터 갈라졌는지**까지 알려준다.

그리고 저 유닛·확장·테크 집계가 자동 대전 밸런싱 도구의 출력 형식이다. 지금은 경기 하나를 보지만, 같은 집계를 수천 경기에 돌리면 매치업 승률표가 된다.

> 저장은 기본적으로 **메모리**다(최근 50개). `REPLAY_DIR`을 설정하면 디스크에도 쓰고 재시작 시 복원한다. 다만 Fly.io 머신 디스크는 볼륨을 붙이지 않으면 재배포 때 사라지므로, 영구 보관은 별도 작업이다.

## 테스트

```bash
pnpm --filter @royale/shared test         # 결정론 단위 테스트 (52개)
pnpm --filter @royale/server test:e2e     # 실제 서버 + 클라 2개 프로세스로 넷코드 검증
pnpm --filter @royale/server test:replay  # 경기를 끝까지 돌려 리플레이 저장·재현 검증
```

E2E는 진짜 서버 프로세스를 띄우고, **서로 다른 종족을 고른** 독립된 두 클라이언트가
확장하고 병력을 뽑는 동안 **같은 틱의 상태 해시가 일치하는지**와
**서버가 리싱크를 한 번도 보내지 않았는지**를 확인한다.
비대칭 대전은 양쪽 시뮬이 서로 다른 테크트리와 유닛 테이블을 참조한다는 뜻이라, 미러전보다 깨지기 쉽다.

```
▶ 매치 성립 (A=team0, B=team1, 종족=steel vs swarmhive)
tick 400 해시 → A=3762083748 B=3762083748
배치 시도: A=9 B=10 / 리싱크: A=0 B=0
공통 틱 20개에서 해시 전부 일치
✅ E2E 통과
```

## 배포

| 대상 | 플랫폼 | 이유 |
|------|--------|------|
| 서버 | **Fly.io** (`fly.toml`) | WebSocket 지원, 리전 선택으로 지연 관리 |
| 클라이언트 | **GitHub Pages** (Actions) | 정적 파일이면 충분 |

```bash
fly launch --no-deploy
fly deploy
```

GitHub Pages 쪽은 `Settings → Pages → Source: GitHub Actions` 로 켜고,
`Settings → Variables → Actions` 에 `VITE_SERVER_URL = wss://<앱이름>.fly.dev` 를 넣으면 된다.

> GitHub Pages는 정적 호스팅이라 WebSocket 서버를 올릴 수 없다. 서버는 반드시 별도 호스팅이 필요하다.

`auto_stop_machines`를 **끄는 것이 중요하다.** 매치 상태가 프로세스 메모리에 있어서, 머신이 멈추면 진행 중인 경기가 통째로 사라진다.

항목별 체크리스트와 완료 기준은 [계획서](docs/PLAN.md)에 있다.

**M7(아트)이 먼저인 이유**는 지금 화면이 도형뿐이라 재미를 판단할 수 없기 때문이다. 무엇이 무엇을 때리는지 안 보이는 상태에서는 밸런스 수치가 좋은지 나쁜지 감이 오지 않는다.

**M8(밸런싱)**: 종족이 3개라 매치업은 6개이고, 여기에 "일꾼 우선 / 테크 우선 / 병력 우선"이라는 전략 축이 곱해진다. 손으로 밸런싱할 규모가 아니라서, 시뮬이 순수 함수라는 성질을 이용해 **헤드리스 자동 대전으로 승률표를 뽑는 도구**를 만든다. 리플레이 요약이 이미 유닛·확장·테크를 종류별로 집계하므로 그게 그대로 출력 형식이 된다.

현재 수치는 역할 구조에 맞춘 초기값이지 검증된 밸런스가 아니다. 이미 보이는 이슈는 [기획서 §12](docs/GAME_DESIGN.md)에 적어 두었다.
